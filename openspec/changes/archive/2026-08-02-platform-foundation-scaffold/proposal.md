## Why

仓库目前只有产品 PRD 与 Cursor/OpenSpec 约定，尚无前后端工程与可运行的平台底座。一期目标是按 PRD 交付**完整健身房运营**（会籍、课程、教练、商品库存、营销、报表、器材、会员小程序/H5、门禁、线上线下支付），但必须先把平台底座脚手架搭稳，否则业态功能会反复推倒。本 change 只负责底座；完整运营由后续 change 连续交付，不削减一期范围。依据：`docs/superpowers/specs/2026-08-02-gym-prd-modules-design.md`。

## What Changes

- 建立根目录 Docker Compose 与 `frontend/`（Vue 3）、`backend/`（Python）独立工程骨架，含健康检查、配置注入、`.env.example`（**脚手架必须可稳定启动与冒烟**）
- 落地平台组织：场地、商户类型、商户；预置角色与员工账号；商户数据隔离
- 落地场地级会员主档（手机号唯一）及商户关联能力
- 落地门禁点、人脸 Pad 设备注册/心跳、通行授权与通行校验/事件（同步可异步）
- 落地订单/支付状态机骨架（线下登记 + 线上支付接口占位），供会籍等业务挂接
- 管理后台最小页面：登录、组织与员工、会员、门禁设备基础管理（为后续健身业态 UI 留好路由与权限骨架）

## 一期完整交付承诺（不在本 change，但必须做）

下列能力属于一期完整健身房运营，**不会取消**；本 change 归档后按切片连续 propose/apply：

1. 会籍与卡种、办卡/续费、与门禁授权联动；线上支付对接（含微信等）与线下登记闭环  
2. 私教/团课、教练、排课预约、核销  
3. 商品库存、营销（券/活动/体验卡）  
4. 报表与财务看板、健身房器材台账与报修  
5. 会员小程序/H5（查卡、约团课、购卡买课、支付、本人通行记录等，对齐 PRD）

## Non-goals（仅限本 change）

以下表示「**本施工单不做**」，不是「项目不做」：

- 本 change 不实现健身房业态完整功能（会籍细则、私教/团课、库存、营销、报表、器材、小程序完整页）— 见上一节后续切片  
- 本 change 不做真实微信商户进件与生产环境支付联调（骨架先落地；线上支付完整联调放在会籍/支付切片）  
- 项目级不做（一期仍不做）：酒吧 POS / 台位等非健身业态包；完整会计总账；分销裂变；物联网器械工况采集  

## Capabilities

### New Capabilities

- `project-scaffold`: 前后端分离工程结构、Compose 编排、配置与本地可启动验证
- `organization`: 场地、商户类型、商户生命周期与归属关系
- `identity-access`: 员工账号、预置角色（超管/商户管理员/前台/教练）、鉴权与商户级数据隔离、关键操作审计
- `member-profile`: 场地级会员主档、手机号唯一、商户关联
- `access-control`: 门禁点、Pad 设备、通行授权、通行校验与事件、异步同步约束
- `commerce-skeleton`: 可扩展订单类型、支付（线下登记 + 线上占位）、退款状态机与流水

### Modified Capabilities

- （无；`openspec/specs/` 尚为空，本 change 全部为新建能力）

## Impact

- 新增/填充：`frontend/`、`backend/`、根目录 `docker-compose.yml`、`.env.example`、`.gitignore`、`README.md`
- 依赖：PostgreSQL（必需）；RabbitMQ（门禁同步/通知按需启用）
- API：组织、认证授权、会员、门禁、订单支付骨架的首批 REST 接口
- 后续 change 将依赖本底座的商户隔离、会员主档、授权与订单模型，直至一期完整健身房运营验收（对齐 PRD 成功标准）
